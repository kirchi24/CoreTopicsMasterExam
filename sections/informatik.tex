\section{Informatik}

\subsection{Relationale vs. multidimensionale Datenbanken}

\definition{\textbf{Datenbanken} (DB) sind strukturierte, persistente Sammlungen von Daten. Ein \textbf{Datenbankmanagementsystem} (DBMS) ist die Software zur Verwaltung dieser Datenbanken (z.\,B.\ PostgreSQL, Oracle, MySQL).}

Im Kern unterscheiden sich Datenbanksysteme durch ihren Einsatzzweck. Geschäftsanwendungen benötigen Systeme, die schnelle, kleine Schreib- und Leseoperationen auf aktuellen Daten durchführen. Im Gegensatz dazu erfordert die analytische Auswertung von Geschäftsdaten ein anderes Paradigma -- komplexe Abfragen über große Datenvolumina mit weniger Fokus auf minimale Latenz.

\definition{\textbf{OLTP} (Online Transaction Processing) ist das Verarbeitungsparadigma für operative Systeme. Transaktionen sind klein, häufig und fokussiert auf Schreib- oder Lesezugriffe einzelner Records. Typische Antwortzeiten liegen im Millisekundenbereich. Beispiele sind Bankensysteme, Webshops oder Buchungssysteme, bei denen eine hohe Anzahl von Benutzern gleichzeitig Daten ändern und lesen.}

\definition{\textbf{OLAP} (Online Analytical Processing) serviert analytische Anfragen über historische Daten. Diese Queries sind komplex, lesen große Mengen an Daten und führen Aggregationen durch. Antwortzeiten können Sekunden bis Minuten betragen, was akzeptabel ist. Typische Anwendungen sind Business Intelligence, Reporting und Data Mining.}

Diese unterschiedlichen Anforderungen führen zu unterschiedlichen Datenmodellen. OLTP-Systeme speichern Daten \textbf{normalisiert} (3NF, BCNF) -- Redundanzen werden minimiert, um Update-Anomalien zu vermeiden. OLAP-Systeme hingegen \textbf{denormalisieren} bewusst, indem sie Daten redundant speichern, um Lesezugriffe zu optimieren. Die Normalisierung verursacht JOIN-Operationen; bei OLAP würde dies unerwünschte Performance-Einbußen bedeuten.

\definition{\textbf{Data Warehouses} (DWH) sind zentrale, integrierte und historisierte Datenbases, speziell für analytische Abfragen optimiert. Daten fließen von verschiedenen OLTP-Systemen via \textbf{ETL-Prozesse} (Extract, Transform, Load) in den Warehouse.}

Im Data Warehouse organisieren sich Daten typischerweise nach zwei Schema-Mustern. Das \textbf{Star-Schema} ist einfach und verständlich: Eine zentrale \textbf{Faktentabelle} enthält Measures (Kennzahlen wie Umsatz, Gewinn, Menge) und Foreign Keys zu mehreren \textbf{Dimensionstabellen} (Zeit, Produkt, Region, Kunde). Der Name resultiert aus der grafischen Darstellung -- die Faktentabelle in der Mitte, Dimensionen rings herum. Das alternative \textbf{Snowflake-Schema} normalisiert die Dimensionstabellen weiter, indem es Hierarchien explizit modelliert (z.B. Produkt -> Kategorie -> Hersteller). Dies spart Speicher, erschwert aber Queries durch zusätzliche JOINs.

Der Kern von OLAP ist der \textbf{Datenwürfel} -- eine n-dimensionale Struktur, bei der jede Dimension eine Hierarchie repräsentiert. Die zeitliche Dimension könnte sein: Jahr -> Quartal -> Monat -> Tag. Die geografische: Kontinent -> Land -> Stadt -> Bezirk. Innerhalb dieses Würfels können Benutzer mehrere klassische Operationen durchführen: \textbf{Slice} (eine Dimension fixieren, z.B. nur 2023), \textbf{Dice} (einen Teilwürfel auswählen, z.B. 2023 und Region='Europa'), \textbf{Drill-Down} (zu detaillierteren Ebenen navigieren) und \textbf{Roll-Up} (zu aggregierten Ebenen aufsteigen).

Für die Implementierung von OLAP gibt es drei Architekturen. \textbf{MOLAP} (Multidimensional OLAP) speichert Daten direkt in Speicherkuben -- extrem schnell für typische Queries, benötigt aber viel RAM. \textbf{ROLAP} (Relational OLAP) speichert alles in Standard-Relationstabellen und berechnet Würfel on-the-fly -- flexibler und skalierbarer, aber langsamer. \textbf{HOLAP} (Hybrid OLAP) kombiniert beide: häufig abgerufene Aggregationen im Speicher, detaillierte Daten relational.

Eine neuere Alternative ist der \textbf{Data Lake} -- ein Repository, das Rohdaten in beliebigem Format speichert (strukturiert, semi-strukturiert, unstrukturiert). Data Lakes sind flexibler als Data Warehouses und ermöglichen exploratives Arbeiten. Sie erfordern aber stärkere Governance und Datenqualität-Management, um nicht zur ``Data Swamp'' zu degenerieren.

\subsection{Entity-Relationship-Modell}

\definition{Das \textbf{Entity-Relationship-Modell} (ERM) ist ein konzeptionelles Modellierungsverfahren zur Abbildung der fachlichen Realität (\textit{Miniwelt}) in eine Datenbankstruktur. Es besteht aus drei Kernkomponenten: \textbf{Entities} (Objekttypen der Realität, z.B. Person, Produkt), \textbf{Attribute} (Eigenschaften dieser Objekte, z.B. Name, Geburtsdatum) und \textbf{Relationships} (Beziehungen zwischen Entitäten).}

Das ERM ist ein konzeptionelles Modell -- es versucht, die fachliche Logik zu erfassen, bevor technische Implementierungsdetails in Betracht gezogen werden. Die typische Modellierungskaskade verläuft über drei Ebenen: Zunächst erfolgt die \textbf{konzeptionelle} Modellierung (ER-Modell), die die Geschäftslogik in ihrer natürlichen Form abbildet. Dann folgt die \textbf{logische} Modellierung, bei der das ER-Modell in ein relationales Schema (Tabellen, Spalten, Schlüssel) transformiert wird. Abschließend erfolgt die \textbf{physische} Modellierung, die sich damit befasst, wie und wo die Daten im DBMS tatsächlich gespeichert werden.

Zentral für das Verständnis von Relationships sind die **Kardinalitäten** -- sie beschreiben, wie viele Entitäten auf jeder Seite einer Beziehung beteiligt sein können. Eine 1:1-Beziehung (z.B. Person-Reisepass) bedeutet, dass jede Person höchstens einen Pass hat und jeder Pass genau zu einer Person gehört. Eine 1:N-Beziehung (z.B. Abteilung-Mitarbeiter) bedeutet, dass eine Abteilung viele Mitarbeiter haben kann, aber ein Mitarbeiter nur in einer Abteilung arbeitet. Eine N:M-Beziehung (z.B. Student-Kurs) bedeutet, dass Studenten in vielen Kursen sein können und Kurse viele Studenten haben können.

Zusätzlich zu Kardinalitäten gibt es **Optionalitäten** (auch Teilnahmebedingungen genannt). Eine Beziehung kann optional sein (0..N) -- nicht jede Entität muss teilnehmen -- oder verpflichtend (1..N). Graphisch werden diese in ER-Diagrammen durch Linien und Symbole dargestellt: Eine Linie mit einfachem Endpunkt bedeutet 1, eine mit Krähenfuß bedeutet N.

Ein wichtiges Konzept sind **schwache Entitäten**. Im Gegensatz zu starken Entitäten, die einen eigenen eindeutigen Schlüssel besitzen (z.B. Mitarbeiternummer), besitzen schwache Entitäten keinen vollständigen eigenen Schlüssel. Stattdessen werden sie durch eine identifizierende Beziehung zu einer starken Entität bestimmt. Ein klassisches Beispiel: Eine Bestellposition ist schwach abhängig von der Bestellung -- die Position kann nur eindeutig identifiziert werden durch die Kombination von Bestellnummer und Positionsnummer.

Das ER-Modell wird dann in das \textbf{relationale Modell} transformiert. Die fundamentalen Konzepte sind: Eine \textbf{Relation} ist eine Tabelle; ein \textbf{Tupel} ist eine Zeile (ein Datensatz); ein \textbf{Attribut} ist eine Spalte. Die \textbf{Domäne} eines Attributs definiert den Wertebereich, z.B. alle positiven Ganzzahlen oder alle Zeichenketten bis 50 Zeichen.

Die Abbildung erfolgt systematisch: Jeder Entity-Typ wird zu einer Tabelle; die Attribute des Entity werden zu Spalten. Bei Relationships muss fallweise unterschieden werden: 1:N-Beziehungen werden durch einen **Fremdschlüssel** (Foreign Key, FK) auf der N-Seite realisiert. N:M-Beziehungen erfordern eine separate **Verbindungstabelle** (Junction Table) mit Foreign Keys zu beiden Entitäten. 1:1-Beziehungen können entweder durch FK oder durch Zusammenführung der Relationen realisiert werden.

  \centering
  \begin{tabularx}{\linewidth}{L{2.5cm} L{4cm} L{8.5cm}}
    \textbf{Schlüsseltyp} & \textbf{Eigenschaft} & \textbf{Beschreibung und Verwendung}                                                \\
    \midrule
    Superkey              & Eindeutig            & Attributkombination, die Tupel eindeutig identifiziert (z.B. \{PersNr, Name\})      \\

Die Integrität relationaler Daten wird durch drei fundamentale Bedingungen gewährleistet. Die \textbf{Entitätsintegrität} fordert, dass der Primärschlüssel eindeutig und nicht NULL ist -- kein Datensatz kann doppelt vorkommen und muss identifizierbar sein. Die \textbf{referentielle Integrität} fordert, dass jeder Fremdschlüssel entweder NULL ist oder auf einen existierenden Primärschlüssel verweist -- es können keine Beziehungen zu nicht-existierenden Entitäten eingefügt werden. Die \textbf{Domänenintegrität} stellt sicher, dass Attributwerte innerhalb ihrer Domäne liegen.

\subsection{SQL als Data Query Language}

\definition{\textbf{SQL} (Structured Query Language) ist die standardisierte Abfragesprache für relationale Datenbanksysteme. Sie wird typisiert in mehrere Kategorien: \textbf{DQL} (Data Query Language -- SELECT-Abfragen), \textbf{DML} (Data Manipulation Language -- INSERT, UPDATE, DELETE), \textbf{DDL} (Data Definition Language -- CREATE, ALTER, DROP), \textbf{DCL} (Data Control Language -- GRANT, REVOKE) und \textbf{TCL} (Transaction Control Language -- COMMIT, ROLLBACK).}

Eine SQL-SELECT-Abfrage durchläuft bei der Ausführung nicht die Klauseln in der geschriebenen Reihenfolge. Stattdessen gibt es eine \textbf{logische Ausführungsreihenfolge}, die es dem Optimierer ermöglicht, Abfragen effizient zu planen. Diese Reihenfolge ist entscheidend zum Verständnis: (1) FROM -- Quellentabelle(n) laden, (2) WHERE -- Zeilenfilterung (Selektion auf Basis von Bedingungen), (3) GROUP BY -- Gruppierung nach Attributen, (4) HAVING -- Filterung auf Gruppen (nicht auf einzelne Zeilen!), (5) SELECT -- Spaltenprojektion und Transformationen, (6) ORDER BY -- Sortierung, (7) LIMIT/OFFSET -- Paginierung.

Das Verständnis dieser Reihenfolge ist essentiell. Viele Anfänger schreiben ORDER BY, als würde es als Erstes evaluiert -- dabei wird es erst am Ende angewendet. Ebenso ist es ein häufiger Fehler, in WHERE-Klauseln Aggregatfunktionen zu verwenden -- dies funktioniert nicht, weil WHERE vor GROUP BY evaluiert wird. Für Bedingungen auf Aggregaten muss HAVING verwendet werden.

\definition{\textbf{NULL-Semantik} in SQL ist nicht intuitiv: NULL bedeutet ``unbekannt'', nicht ``Null-Wert'' oder ``leerer String''. Ein Vergleich `wert = NULL` ergibt nicht FALSE, sondern UNKNOWN -- eine dreiwertige Logik. Die Konsequenz: NULL-Vergleiche funktionieren nicht mit Operatoren; stattdessen muss `IS NULL` oder `IS NOT NULL` verwendet werden.}

WHERE-Klauseln akzeptieren verschiedene Vergleichsoperatoren und Funktionen. Die klassischen sind: \texttt{=, <>, >, <, >=, <=}. Zusätzlich gibt es \texttt{BETWEEN} für Bereiche (z.B. \texttt{preis BETWEEN 10 AND 100}), \texttt{IN} für Mengen (z.B. \texttt{stadt IN ('Wien', 'Graz')}), und \texttt{LIKE} für Mustererkennung, die \texttt{\_} (genau ein beliebiges Zeichen) und \texttt{\%} (beliebig viele Zeichen) verwendet.

**Aggregatfunktionen** fassen mehrere Zeilen zu einem Ergebnis zusammen: `COUNT(*)` zählt alle Zeilen (auch mit NULL), während `COUNT(spalte)` nur Nicht-NULL-Werte zählt. `SUM()` addiert Werte, `AVG()` berechnet Mittelwerte, `MIN()`/`MAX()` finden Extremwerte. Ohne GROUP BY wird eine einzelne Aggregation über alle Zeilen berechnet.

**JOINs** sind das Herzstück von SQL für die Kombination mehrerer Tabellen. Ein `INNER JOIN` gibt nur Zeilen zurück, bei denen beide Tabellen ein Match für die Join-Bedingung haben. Ein `LEFT JOIN` gibt alle Zeilen der linken Tabelle zurück; bei fehlenden Matches wird die rechte Seite mit NULL aufgefüllt. Analog funktioniert `RIGHT JOIN` andersherum. `FULL OUTER JOIN` gibt alle Zeilen aus beiden Tabellen zurück. Ein `CROSS JOIN` erzeugt das kartesische Produkt -- alle Kombinationen zwischen beiden Tabellen.

Weitere nützliche Konzepte sind: `DISTINCT` entfernt Duplikate aus Ergebnissen; **Subqueries** ermöglichen verschachtelte SELECT-Abfragen in WHERE-, FROM- oder SELECT-Klauseln; **Views** sind virtuelle Tabellen, die auf Basis von Queries definiert werden; **Indizes** beschleunigen Suchzugriffe; `COALESCE(a,b,...)` gibt den ersten Nicht-NULL-Wert zurück.

  \centering
  \begin{tabularx}{\linewidth}{L{2.5cm} L{4.5cm} L{7.5cm}}
    \textbf{Operator/Funktion} & \textbf{Beispiel}               & \textbf{Beschreibung}                    \\
    \midrule
    BETWEEN                    & preis BETWEEN 10 AND 100        & Wertebereich (inklusive Grenzen)         \\
    IN                         & stadt IN ('Wien','Graz','Linz') & Wert muss in Menge enthalten sein        \\

\subsection{Normalformen, Integritätsbedingungen und Transaktionen}

\definition{\textbf{Normalisierung}} ist die systematische Umstrukturierung eines Relationenschemas, um Redundanzen zu reduzieren und Anomalien zu vermeiden. Ohne Normalisierung entstehen typische Probleme: **Insert-Anomalien** treten auf, wenn neue Entitäten nicht eingefügt werden können, ohne irrelevante Daten hinzuzufügen. **Update-Anomalien** entstehen, wenn eine Information an mehreren Stellen gepflegt werden muss, was Inkonsistenzen riskiert. **Delete-Anomalien** treten auf, wenn das Löschen einer Entität zu ungewolltem Datenverlust führt.

Die Normalformen bilden eine Hierarchie von immer strengeren Anforderungen. Die \textbf{1. Normalform (1NF)} fordert, dass alle Attributwerte atomar (unteilbar) sind und keine Wiederholungsgruppen existieren. Ein Beispiel für Verletzung: eine Spalte Hobbys mit dem Wert Lesen, Schwimmen, Joggen -- dies müsste stattdessen auf mehrere Zeilen verteilt sein.

Die \textbf{2. Normalform (2NF)} fordert 1NF plus: Es darf keine partiellen Abhängigkeiten geben. Dies ist relevant, wenn der Primärschlüssel aus mehreren Attributen besteht (zusammengesetzter Schlüssel). Eine partielle Abhängigkeit liegt vor, wenn ein Nicht-Schlüssel-Attribut nur von einem Teil des zusammengesetzten Schlüssels abhängt. Ein Beispiel: Tabelle (StudentenID, KursID, KursName) -- KursName hängt nur von KursID ab, nicht von der Kombination.

Die \textbf{3. Normalform (3NF)} fordert 2NF plus: Es darf keine transitiven Abhängigkeiten geben. Das heißt, kein Nicht-Schlüssel-Attribut darf von einem anderen Nicht-Schlüssel-Attribut abhängen. Ein Beispiel: (PersonenID, Name, AbteilungsID, AbteilungsName) -- AbteilungsName hängt von AbteilungsID ab, nicht direkt vom PK PersonenID.

Die \textbf{Boyce-Codd-Normalform (BCNF)} ist strenger als 3NF. Sie fordert, dass für jede funktionale Abhängigkeit $X \to Y$ die linke Seite $X$ ein Superschlüssel sein muss. BCNF eliminiert pathologische Spezialfälle, die in 3NF noch vorkommen können.

In der Praxis werden die meisten kommerziellen Datenbanken in 3NF modelliert, weil sie einen guten Kompromiss zwischen Redundanzreduktion und Query-Performance darstellt. Höhere Normalformen (BCNF, 4NF, 5NF) sind theoretisch eleganter, führen aber oft zu übermäßig fragmentierten Schemas mit vielen JOINs.

Integritätsbedingungen sichern die Konsistenz. Der bereits erwähnte **PRIMARY KEY** erzwingt Eindeutigkeit und NOT NULL. Ein **FOREIGN KEY** sorgt für referentielle Integrität -- er referenziert einen PK einer anderen Tabelle (oder NULL). Ein **UNIQUE**-Constraint macht ein Attribut eindeutig, erlaubt aber mehrfach NULL. **NOT NULL** erzwingt, dass ein Wert eingegeben werden muss. Ein **CHECK**-Constraint validiert Bedingungen (z.B. `ALTER TABLE Produkt ADD CHECK (Preis > 0)`). Ein **DEFAULT**-Wert wird automatisch eingesetzt, wenn beim Insert kein Wert angegeben wird.

Referentielle Aktionen definieren das Verhalten bei Änderungen. Mit `ON DELETE CASCADE` werden abhängige Zeilen automatisch gelöscht. `ON DELETE SET NULL` setzt den FK auf NULL. `ON DELETE RESTRICT` (oder `NO ACTION`) verweigert die Löschung, wenn noch Abhängigkeiten bestehen.

\definition{Eine \textbf{Transaktion}} ist eine logische Einheit mehrerer Datenbankoperationen. Alle Operationen werden entweder vollständig (COMMIT) oder gar nicht (ROLLBACK) ausgeführt -- ein Alles-oder-Nichts-Prinzip.

Transaktionen müssen die **ACID-Eigenschaften** erfüllen: \textbf{Atomicity} (Atomarität) -- eine Transaktion ist unteilbar, entweder erfolgreich oder komplett rückgängig; \textbf{Consistency} (Konsistenz) -- die Datenbank bleibt in konsistentem Zustand, alle Integritätsbedingungen werden erfüllt; \textbf{Isolation} (Isolation) -- parallel laufende Transaktionen beeinflussen sich gegenseitig nicht; \textbf{Durability} (Dauerhaftigkeit) -- committete Daten sind persistent und bleiben selbst nach Systemausfällen erhalten.

Die Isolationslevel beschreiben, wie sehr sich parallele Transaktionen gegenseitig beeinflussen dürfen. Vier sind standardisiert (aufsteigend in Strenge): \textbf{Read Uncommitted} (niedrigster Standard) erlaubt \textbf{Dirty Reads} -- eine Transaktion kann Änderungen sehen, die von einer parallelen Transaktion noch nicht committiert wurden. \textbf{Read Committed} verhindert Dirty Reads, aber erlaubt **Non-repeatable Reads** -- innerhalb einer Transaktion kann sich ein Wert ändern zwischen zwei Lesezugriffen. \textbf{Repeatable Read} verhindert Non-repeatable Reads, aber erlaubt **Phantom Reads** -- zwischen zwei Abfragen können neue Zeilen eingefügt werden, die die Aggregationen ändern. \textbf{Serializable} ist der höchste Level und verhindert alle Anomalien durch seriellen Zugriff (ist aber oft unpraktisch langsam).

\definition{\textbf{Write-Ahead Logging (WAL)}} ist ein Mechanismus zur Sicherung der Durability. Änderungen werden zuerst ins Log geschrieben, bevor sie in die Datenbank übernommen werden. Im Fehlerfall kann der Zustand aus dem Log rekonstruiert werden.

\subsection{Datenschutz und Datensicherheit}

\subsubsection{Begriffsabgrenzung}

\textbf{Datenschutz} und \textbf{Datensicherheit} werden im Alltag oft synonym verwendet, bezeichnen aber unterschiedliche Konzepte:

\begin{itemize}
  \item \textbf{Datenschutz} (engl. \textit{data privacy}) ist das \textbf{rechtliche und organisatorische} Konzept, das den Schutz personenbezogener Daten natürlicher Personen vor unbefugter Verarbeitung sicherstellt. Es geht primär um die Frage: \emph{Darf} ein Unternehmen diese Daten überhaupt erheben und verarbeiten?
  \item \textbf{Datensicherheit} (engl. \textit{data security / information security}) ist das \textbf{technische und organisatorische} Konzept, das alle Daten -- unabhängig ob personenbezogen -- vor Verlust, Manipulation, unbefugtem Zugriff und anderen Bedrohungen schützt. Es geht um die Frage: \emph{Wie} werden Daten technisch gesichert?
\end{itemize}

\subsubsection{Rechtlicher Rahmen: DSGVO}

Die \textbf{Datenschutz-Grundverordnung} (DSGVO), in Kraft seit Mai 2018, ist die maßgebliche europäische Rechtsgrundlage für den Umgang mit personenbezogenen Daten. Sie gilt für alle Unternehmen, die Daten von EU-Bürgern verarbeiten -- unabhängig vom Unternehmensstandort.

\textbf{Grundsätze der DSGVO:}
\begin{enumerate}
  \item \textbf{Rechtmäßigkeit, Transparenz:} Verarbeitung braucht eine Rechtsgrundlage (Einwilligung, Vertrag, rechtliche Verpflichtung, berechtigte Interessen)
  \item \textbf{Zweckbindung:} Daten dürfen nur für den bei der Erhebung festgelegten Zweck verwendet werden
  \item \textbf{Datenminimierung:} Es dürfen nur die Daten erhoben werden, die für den Zweck erforderlich sind
  \item \textbf{Richtigkeit:} Daten müssen korrekt und aktuell sein
  \item \textbf{Speicherbegrenzung:} Speicherung nur solange nötig
  \item \textbf{Integrität und Vertraulichkeit:} Datenschutz durch Maßnahmen
  \item \textbf{Rechenschaftspflicht:} Der Verantwortliche muss Einhaltung nachweisen
\end{enumerate}

\textbf{Betroffenenrechte:} Recht auf Auskunft, Berichtigung, Löschung (``Recht auf Vergessenwerden''), Datenportabilität, Widerspruch gegen automatisierte Entscheidungen.

\textbf{Sanktionen:} Verstöße können mit bis zu \textbf{20 Millionen Euro} oder \textbf{4\,\% des weltweiten Jahresumsatzes} geahndet werden.

\subsubsection{CIA-Modell der Informationssicherheit}

Das klassische Rahmenwerk definiert drei Schutzziele:

\begin{itemize}
  \item \textbf{Confidentiality (Vertraulichkeit):} Unbefugte dürfen nicht auf Daten zugreifen. Maßnahmen: Verschlüsselung, Zugriffskontrolle
  \item \textbf{Integrity (Integrität):} Daten dürfen nicht unbefugt verändert werden. Maßnahmen: Hashwerte, digitale Signaturen
  \item \textbf{Availability (Verfügbarkeit):} Autorisierte Benutzer sollen jederzeit auf Daten zugreifen können. Maßnahmen: Redundanz, Backups, DDoS-Schutz
\end{itemize}

\subsubsection{Technische und organisatorische Maßnahmen}

Die DSGVO verlangt ``Privacy by Design'' sowie angemessene TOMs:

\textbf{Wichtige Maßnahmen:}
\begin{itemize}
  \item Pseudonymisierung und Anonymisierung
  \item Verschlüsselung (AES-256 für Daten, TLS 1.3 für Übertragung)
  \item Role-Based Access Control (RBAC)
  \item Backups nach 3-2-1-Regel (3 Kopien, 2 Medientypen, 1 Off-site)
  \item Umfassendes Logging und Auditing
  \item Regelmäßige Schulungen der Mitarbeiter
\end{itemize}

\subsubsection{Datenschutz im ML/Data-Science-Kontext}

In Data-Science-Projekten ergeben sich spezifische Herausforderungen:

\begin{itemize}
  \item \textbf{Datenvergiftung:} Unvorsichtige Nutzung von Trainingsdaten kann zu Datenlecks führen
  \item \textbf{Model Inversion:} ML-Modelle können trainierte Daten teilweise rekonstruieren
  \item \textbf{Fairness und Bias:} Diskriminierende Modelle verletzen DSGVO
  \item \textbf{Datentransfers:} Übermittlung von EU-Daten in Drittländer ist oft nicht zulässig
\end{itemize}

\subsection{Python: Listen, Tupel und Mengen}

\definition{\textbf{Listen} (\texttt{list}), \textbf{Tupel} (\texttt{tuple}) und \textbf{Mengen} (\texttt{set}) sind fundamentale Python-Datenstrukturen für Sammlungen. Sie unterscheiden sich in ihren Eigenschaften: Veränderbarkeit, Ordnung, Eindeutigkeit und Verwendbarkeit als Dictionary-Keys.}

Alle drei sind iterierbar -- man kann sie in \texttt{for}-Schleifen durchlaufen. Alle unterstützen den \texttt{in}-Operator für Mitgliedschaftstests und die built-in Funktionen \texttt{len()}, \texttt{min()}, \texttt{max()} und \texttt{sum()}. Entscheidend sind aber ihre Unterschiede.

Die \textbf{Liste} ist die am häufigsten verwendete Struktur. Sie ist \textbf{geordnet} (die Einfügereihenfolge bleibt erhalten), \textbf{veränderlich} (mutable) -- Elemente können hinzugefügt, entfernt und modifiziert werden -- und erlaubt Duplikate. Listen unterstützen Index-Zugriffe in $\mathcal{O}(1)$, aber Einfügungen an beliebigen Positionen kosten $\mathcal{O}(n)$, weil nachfolgende Elemente verschoben werden müssen. Typisch werden Listen für dynamische Sammlungen verwendet: während Schleifen wachsende Ergebnisse, Puffern von Daten, oder Warteschlangen.

Das \textbf{Tupel} ist konzeptuell wie eine Liste, aber \textbf{unveränderlich} (immutable). Hat man ein Tupel, kann man es nicht mehr ändern -- keine \texttt{append()}, \texttt{remove()}-Methoden. Dieser Constraint bietet zwei Vorteile: Erstens kann ein Tupel als Dictionary-Key verwendet werden (nur hashbare Objekte dürfen Keys sein); Zweitens ist es speichereffizienter als eine Liste, da Python keine Größen-Overhead vorhalten muss. Ein Tupel mit benannten Feldern kann via \texttt{typing.NamedTuple} definiert werden, was Code-Lesbarkeit verbessert. Typisch werden Tupel für Datenbankdatensätze, Funktionsrückgaben (mehrere Werte als Tuple unpacking), oder Konfigurationsparameter verwendet.

Die \textbf{Menge} (set) ist ungeordnet, speichert nur eindeutige Werte, und ist intern als Hash-Tabelle implementiert. Mitgliedschaftstests, Einfügungen und Löschungen sind $\mathcal{O}(1)$ im Durchschnitt. Das gewaltige Vorteil: Wenn man feststellen muss, ob ein Wert in einer großen Kollektion existiert, ist ein set $\mathcal{O}(1)$ schnell, während eine Liste $\mathcal{O}(n)$ Zeit braucht. Mengen unterstützen klassische Mengenoperationen: Vereinigung (\texttt{|}), Schnitt (\texttt{\&}), Differenz (\texttt{-}) und symmetrische Differenz (\texttt{\^}). Das \texttt{frozenset}-Pendant ist unveränderlich und hashbar. Typische Anwendungen sind schnelle Eindeutigkeitstests, Deduplizierung von Listen, oder Mengenlogik (alle Elemente aus A, die nicht in B sind).

\begin{table}[h!]
  \centering
  \begin{tabular}{l c c c}
    \textbf{Eigenschaft} & \textbf{list}    & \textbf{tuple}   & \textbf{set}     \\
    \midrule

    Geordnet             & \checkmark       & \checkmark       & --               \\
    Veränderlich         & \checkmark       & --               & \checkmark       \\
    Duplikate erlaubt    & \checkmark       & \checkmark       & --               \\
    Mitgliedschaftstest  & $\mathcal{O}(n)$ & $\mathcal{O}(n)$ & $\mathcal{O}(1)$ \\
    Hashbar (als Key)    & --               & \checkmark       & --               \\
    Mengenoperationen    & --               & --               & \checkmark       \\
  \end{tabular}
\end{table}

Für Anfänger ist es wichtig zu verstehen, wann welche Struktur die richtige Wahl ist. Benötigt man eine Sammlung mit Indexzugriff, die sich ändert? Dann Liste. Benötigt man einen unveränderlichen Schlüssel oder mehrere Rückgabewerte? Dann Tupel. Muss man schnell testen, ob ein Wert existiert, oder Mengenoperationen durchführen? Dann Set.

\subsection{Python: Kopien vs. Verweise, Shallow \& Deep Copies}

\definition{In Python ist jede Variable ein \textbf{Name} oder Label, das auf ein Objekt im Speicher zeigt. Eine Zuweisung wie \texttt{b = a} kopiert nicht das Objekt, sondern lässt beide Namen auf \textbf{dasselbe Objekt} zeigen. Dies ist eine Referenzsemantik, die viele Python-Anfänger überrascht.}

Der \texttt{is}-Operator prüft Identität (gleiche Speicheradresse), während \texttt{==} Gleichheit (gleicher Wert) prüft. Bei unveränderlichen Typen ist dieser Unterschied oft unsichtbar, weil Python kleinere Integers und kurze Strings intern cached. Bei veränderlichen Typen ist der Unterschied kritisch: zwei Listen können gleich sein (\texttt{==}), aber unterschiedliche Objekte (\texttt{is not}).

Dies unterscheidet sich fundamenttal bei **unveränderlichen Typen** (\texttt{int, float, str, tuple, frozenset}), bei denen scheinbare ``Änderungen'' tatsächlich neue Objekte erzeugen. Wenn man ein Tupel ändern möchte, kann man das nicht -- Python wirft einen Fehler. Stattdessen erstellte man ein neues Tupel. Bei **veränderlichen Typen** (\texttt{list, dict, set}) können Attribute und Elemente in-place verändert werden.

Das hat eine große Konsequenz: Wenn man auf Basis einer Liste mehrere Variablen erstellt, teilen sich alle auf Mutations-Operationen. Ein beliebtes und tückisches Beispiel ist:

\texttt{a = [1, 2, 3]} \\
\texttt{b = a} \\
\texttt{b.append(4)} \\
\texttt{print(a)  \# [1, 2, 3, 4]!}

Um dieses Problem zu lösen, kann man eine **Shallow Copy** erstellen. Dies erzeugt einen neuen Container (die äußerste Ebene), aber die Elemente werden nicht kopiert -- sie werden noch geteilt. Bei verschachtelten Strukturen ist dies oft nicht ausreichend. Wege zur Shallow Copy sind: \texttt{list(orig)}, \texttt{orig[:]}, \texttt{copy.copy(orig)}, oder \texttt{orig.copy()}.

Eine **Deep Copy** erzeugt ein vollständig unabhängiges Objekt inklusive aller rekursiv erreichbaren Unterobjekte. Es gibt keine gemeinsamen mutable Objekte zwischen Original und Kopie. Der Standard-Weg ist \texttt{copy.deepcopy(orig)}. Die Funktion durchquert den gesamten Objektgraph und erstellt eine Kopie jedes Objekts. Es behandelt auch zyklische Referenzen via internes Memo-Dictionary. Deep Copy ist aber erheblich teurer -- für Performance-kritischen Code sollte man sie vermeiden und stattdessen unveränderliche Strukturen oder explizite Rekonstruktion verwenden.

Beim Übergeben von Parametern an Funktionen folgt Python einer **Pass-by-Object-Reference**-Semantik. Die Funktion erhält eine Referenz auf das Objekt. Wenn es veränderlich ist, können Mutationen in der Funktion den Original beeinflussen. Eine Neuzuweisung des Parameters (z.B. \texttt{param = param + 1}) beeinflusst aber nicht die aufrufende Seite.

Ein klassisches Anfänger-Fehler ist die **Default-Argument-Falle**:

\texttt{def f(lst=[]):} \\
\texttt{\ \ \ \ lst.append(1)} \\
\texttt{\ \ \ \ return lst}

Die leere Liste wird einmal bei der Funktionsdefinition erstellt und über alle Aufrufe geteilt! Ruft man \texttt{f()}, \texttt{f()}, \texttt{f()} auf, erhält man \texttt{[1]}, \texttt{[1,1]}, \texttt{[1,1,1]}, nicht dreimal \texttt{[1]}. Die korrekte Lösung:

\texttt{def f(lst=None):} \\
\texttt{\ \ \ \ if lst is None:} \\
\texttt{\ \ \ \ \ \ \ \ lst = []}

\subsection{Python: Schritte des Data-Preprocessings (scikit-learn)}

\definition{\textbf{Data-Preprocessing} ist die systematische Vorbereitung von Rohdaten für Machine-Learning-Algorithmen. Viele Verfahren (SVM, k-NN, neuronale Netze) sind empfindlich gegenüber Skalierungen, fehlenden Werten oder falschen Kodierungen. Schlechte Vorbereitung führt zu systematisch schlechteren Modellen.}

Das scikit-learn-Ökosystem strukturiert Preprocessing um das \textbf{Pipeline-Konzept}: Jeder Schritt hat eine \texttt{fit(X)}-Methode (auf Trainingsdaten lernen) und eine \texttt{transform(X)}-Methode (auf beliebigen Daten anwenden). Mehrere Schritte werden via \texttt{Pipeline} verkettet. Der kritische Punkt ist: \texttt{fit} wird **nur auf Trainingsdaten** aufgerufen! Würde man \texttt{fit} auf kombinierten Trainings- und Testdaten aufrufen, käme es zu **Data Leakage** -- der Test-Set beeinflusst die Preprocessing-Parameter, was unrealistisch optimistische Metriken ergibt.

Der **erste Schritt ist Imputation** -- der Umgang mit fehlenden Werten (NaN, None). \texttt{SimpleImputer} unterstützt mehrere Strategien: \texttt{'mean'} (Durchschnitt, nur für Numerisches), \texttt{'median'} (robust gegen Ausreißer), \texttt{'most\_frequent'} (Modus, gut für kategorische Variablen), \texttt{'constant'} (ein fester Wert). Für komplexere Szenarien ist \texttt{KNNImputer} sinnvoll -- sie imputen basierend auf Nachbar-Werten in anderen Features.

Der **zweite Schritt ist Feature-Skalierung** -- die Normalisierung numerischer Features auf vergleichbare Spannweiten. \texttt{StandardScaler} transformiert zu Z-Werten: $z = (x - \mu) / \sigma$, sodass $\mu=0, \sigma=1$. \texttt{MinMaxScaler} normalisiert auf $[0,1]$: $(x - \min) / (\max - \min)$, ist aber empfindlich gegen Ausreißer. \texttt{RobustScaler} basiert auf dem Interquartilbereich (IQR) und ist ausreißer-robust.

Der **dritte Schritt ist Kodierung kategorischer Features**. \texttt{OrdinalEncoder} konvertiert zu ganzen Zahlen (nur bei echten Ordnungen verwenden!). \texttt{OneHotEncoder} erzeugt binäre Dummy-Variablen -- für Kategorie $i$ wird eine neue Spalte mit 1 an Position $i$ und 0 sonst erstellt. Dies vermeidet implizite Rangfolgen, führt aber zu hochdimensionalen Daten bei vielen Kategorien.

Der **vierter Schritt ist Feature Engineering** -- das Erzeugen neuer Features aus bestehenden. \texttt{PolynomialFeatures} erzeugt Interaktionsterme und potenzen (z.B. aus $x_1, x_2$ werden $x_1^2, x_1 x_2, x_2^2$). \texttt{PowerTransformer} macht schiefe Verteilungen mittels Yeo-Johnson-Transformation annähernd normal, was manche Modelle stabilisiert.

Der **fünfte Schritt ist Feature-Selektion** -- die Reduktion auf relevante Features. \texttt{VarianceThreshold} entfernt konstante oder quasi-konstante Features. \texttt{SelectKBest} wählt die Top-$k$ Features nach einer Teststatistik (z.B. F-Score). \texttt{SelectFromModel} nutzt Feature-Importances eines einfachen ersten Modells zur Auswahl.

Ein kritisches Problem ist **Class Imbalance** -- wenn Klassen extrem unbalanciert sind (z.B. 99\% Negative, 1\% Positive). Das Modell könnte einfach alles als Majoritätsklasse klassifizieren. Abhilfen: SMOTE (synthetisches Oversampling der Minoritätsklasse), oder \texttt{class\_weight='balanced'} im Modell-Konstruktor.

Die \texttt{ColumnTransformer} ist besonders praktisch, wenn verschiedene Features unterschiedliche Transformationen brauchen. Sie wendet verschiedene Pipelines parallel auf verschiedene Feature-Gruppen an -- z.B. numerische Features mit StandardScaler, kategorische mit OneHotEncoder.

\subsection{NumPy -- Einsatzmöglichkeiten und Vorteile gegenüber \glqq plain\grqq{} Python}

\definition{\textbf{NumPy} (Numerical Python) ist die Fundamentalbibliothek für numerisches Rechnen in Python. Sie stellt homogene, multidimensionale Arrays (\texttt{numpy.ndarray}) und eine umfangreiche Sammlung mathematischer Funktionen bereit. NumPy ist die Basis für praktisch alle anderen wissenschaftlichen Bibliotheken: SciPy, pandas, scikit-learn, PyTorch, TensorFlow.}

Der Kern-Vorteil von NumPy ist die **Performance**. Typischerweise ist NumPy 50-100x schneller als plain Python für numerische Operationen. Dies resultiert aus mehreren Faktoren. Erstens: **homogener, kompakter Speicher**. Alle Array-Elemente sind vom gleichen Typ (z.B. \texttt{float64} = 8 Bytes) und liegen zusammenhängend im Speicher -- nicht wie bei Listen, wo jedes Element ein separates Python-Objekt mit Overhead ist. Zweitens: **Vektorisierung**. Operationen werden ohne explizite Python-Schleifen ausgeführt und nutzen SIMD-Instruktionen (SSE, AVX) der CPU. Drittens: **Broadcasting**. Arrays unterschiedlicher Formen können kombiniert werden, ohne Daten zu kopieren. Viertens: **C/Fortran-Kernroutinen**. Die Performance-kritischen Teile sind in C oder Fortran geschrieben, nicht in Python.

Fundamentale Konzepte: Der \texttt{dtype} legt den einheitlichen Datentyp fest (\texttt{float64, int32, bool, complex128}, etc.). Die \texttt{shape} beschreibt die Dimensionen, z.B. \texttt{(100, 28, 28)} für 100 Bilder à 28x28 Pixel. Ein wichtiger und oft übersehener Punkt: Viele Operationen (Slicing, Transpose, Reshape) geben **Views** zurück -- sie teilen sich denselben unterligenden Speicherpuffer mit dem Original. Mit \texttt{arr.base} kann man prüfen, ob ein Array ein View ist.

**Broadcasting-Regeln** ermöglichen elegante vektorisierte Operationen. Die Dimensionen werden von rechts ausgerichtet. Eine Dimension der Größe 1 wird konzeptuell auf die Größe des anderen Arrays ausgedehnt, ohne physische Datenkopie. Beispiel: \texttt{np.array([[1],[2],[3]])} (Shape 3x1) + \texttt{np.array([10, 20, 30])} (Shape (3,)) ergibt Shape (3x3), wo jede Spalte der zweiten addiert wird.

Wichtige Operationen: **Erstellung** via \texttt{np.zeros, np.ones, np.arange, np.linspace, np.random.rand}. **Indexing** wie \texttt{a[2:5]} (Slicing), \texttt{a[::2]} (jeden 2.),  \texttt{a[a > 0]} (Boolean Mask). **Aggregation** via \texttt{sum(), mean(), std(), max(axis=0)} (über erste Achse). **Lineare Algebra** mit \texttt{np.dot}, \texttt{a @ b} (Matrixmultiplikation), \texttt{np.linalg.inv, eig, solve}. **Ufuncs** (\texttt{np.exp, log, sqrt, sin}) sind elementweise vektorisierte Funktionen.

Die Einsatzmöglichkeiten sind vielfältig. Für **Lineare Algebra**: Matrixmultiplikation, Gleichungssysteme, Eigenwertzerlegung, FFT. Für **Machine Learning**: Feature-Matrizen werden als NumPy-Arrays repräsentiert; scikit-learn ist kompatibel; PyTorch-Tensoren können nahtlos aus/zu NumPy konvertiert werden. Für **Bilddaten**: Ein RGB-Bild wird als \texttt{(H, W, 3)}-Array repräsentiert; Normalisierung, Cropping, Filtering sind einfach. Für **Simulation**: ODE-Schritte, Wetterdaten-Interpolation, ohne Python-Schleifen.

Grenzen: NumPy läuft nur auf CPU; für GPU benötigt man CuPy, PyTorch oder TensorFlow. NumPy hat keine automatische Differentiation; dafür sind PyTorch oder JAX zuständig.

\subsection{R: Vektoren, Matrizen, Arrays, DataFrames, Listen}

\definition{\textbf{R} ist eine funktionale, objektorientierte Sprache spezialisiert auf Statistik und Data Science. Die fundamentale Philosophie von R: \textbf{Alles ist ein Vektor}. Sogar ein einzelner Wert ist eigentlich ein Vektor der Länge 1. Die Grunddatenstrukturen unterscheiden sich in Homogenität, Dimensionalität und Verwendungszweck.}

Die **atomare Vektoren** sind die Bausteine. Sie sind homogen (ein Datentyp für alle Elemente) und können typsweise sein: \texttt{numeric} (Fließkommazahlen), \texttt{integer} (Ganzzahlen), \texttt{logical} (TRUE/FALSE), \texttt{character} (Zeichenketten), \texttt{complex} (komplexe Zahlen), \texttt{raw} (Rohdaten). Die zentrale Eigenschaft ist **Vektorisierung**: Operationen wie \texttt{x + y} oder \texttt{sin(x)} arbeiten elementweise ohne explizite Schleife. Das **Recycling**-Prinzip ist praktisch und manchmal tückisch: Ein kurzer Vektor wird automatisch wiederholt, bis seine Länge passt. Vektoren werden typischerweise für numerische Berechnungen, Zeitreihen oder Messreihen verwendet.

**Matrizen** sind 2D-Verallgemeinerungen von Vektoren. Sie sind homogen und spalten-major (wie in Fortran), was für Speicherlayout und Performance-Implikationen wichtig ist. Index-Zugriff erfolgt mit \texttt{[i,j]}. Lineare-Algebra-Operationen sind direkt verfügbar: \texttt{t(M)} transponiert, \texttt{M \%*\% N} ist Matrixmultiplikation. Der Vorteil ist numerische Effizienz und Stabilität; der Nachteil ist, dass nur ein Datentyp per Matrix möglich ist.

**Arrays** sind n-dimensionale Verallgemeinerungen. Sie sind homogen wie Matrizen, aber beliebig-dimensional. Index-Zugriff funktioniert mit \texttt{arr[i1, i2, ..., in]}, und Subsetting mit \texttt{arr[1:5, , 3]} (erste 5 Zeilen, alle Spalten, 3. Slice). Typische Einsätze: Zeitreihenanalyse mit mehreren Variablen, 3D-Daten (z.B. Neuronale-Netze-Preprocessing).

\definition{Der \textbf{Data Frame} ist R's Antwort auf eine relationale Tabelle. Im Gegensatz zu Matrizen ist ein Data Frame \textbf{heterogen} -- Spalten dürfen unterschiedliche Typen haben. Jede Spalte ist ein Vektor (oder faktorisiert), und alle Spalten müssen gleich lang sein. Spalten werden accessed via \texttt{\$}-Operator (\texttt{df\$Name}) oder Bracket-Notation (\texttt{df[, Name]}).}

Data Frames sind das Arbeitspferd von Statistik in R. Sie ermöglichen elegante statistische Formeln: \texttt{lm(y \textasciitilde\ x1 + x2, data=df)} regressiert $y$ auf $x_1$ und $x_2$. Der Vorteil ist Flexibilität und nahtlose Integration mit statistischen Funktionen. Der Nachteil ist, dass Data Frames bei rein numerischen Berechnungen langsamer sind als Matrizen. Moderne Alternativen sind \texttt{tibble} (verbesserter Data Frame mit strikterem Verhalten) und \texttt{data.table} (stark optimiert für große Datenmengen).

**Listen** sind R's generische Vektoren. Elemente einer Liste können beliebige Typen haben -- Zahlen, Strings, andere Listen, Funktionen. Sie sind die flexibelste Struktur. Index-Zugriff erfolgt mit \texttt{list[[i]]} (gibt Element zurück) oder \texttt{list[i]} (gibt Sub-Liste zurück) -- der Unterschied ist subtil aber wichtig. Benannte Elemente werden mit \texttt{list\$name} accessed. Listen werden typischerweise für Funktionsrückgaben (mehrere Objekte) oder komplexe, heterogene Datenstrukturen verwendet. Der Nachteil ist Performance -- Listen sind langsamer als homogene Strukturen.

\begin{table}[h!]
  \centering
  \begin{tabularx}{\linewidth}{L{2.2cm} C{1.8cm} L{4.8cm} L{3.2cm}}
    \textbf{Struktur} & \textbf{Dim} & \textbf{Eigenschaft}     & \textbf{Use-Case}                        \\
    \midrule
    Vektor            & 1D           & Homogen, vektorisiert    & Numerische Sequenzen, Zeitreihen         \\
    Matrix            & 2D           & Homogen, spalten-major   & Lineare Algebra, numerische Berechnungen \\
    Array             & nD           & Homogen, beliebig        & Multidimensionale Daten, Simulationen    \\
    Data Frame        & 2D           & Heterogen (spaltenweise) & Statistische Analyse, Tabellen           \\
    Liste             & nD           & Heterogen, rekursiv      & Komplexe Strukturen, Rückgabewerte       \\
  \end{tabularx}
\end{table}

\subsection{Objektorientierte Programmierung in R}

\subsubsection{Überblick und Besonderheit}

R ist primär eine funktionale Sprache -- OOP ist ein nachträglich hinzugefügtes Konzept. Deshalb gibt es \textbf{mehrere, teils konkurrierende OOP-Systeme}, die historisch gewachsen sind. Die vier wichtigsten sind: \textbf{S3}, \textbf{S4}, \textbf{R5 (Reference Classes)} und \textbf{R6}.

\subsubsection{S3 -- Informelles Dispatch-System}

S3 ist das älteste und am häufigsten verwendete OOP-System in R. Es basiert auf \textbf{generischen Funktionen und Method Dispatch}: Eine generische Funktion (z.\,B.\ \texttt{print}, \texttt{summary}, \texttt{plot}) ruft die passende Methode auf Basis des \texttt{class}-Attributs des ersten Arguments auf.

\textbf{Method Dispatch:} Wenn \texttt{speak(fido)} aufgerufen wird, sucht R nach \texttt{speak.Dog}, dann \texttt{speak.default}. Die Vererbung wird über den \texttt{class}-Vektor mit mehreren Einträgen realisiert.

\textbf{Vorteile:} Extrem leichtgewichtig; keine formale Definition nötig; kompatibel mit den meisten Base-R-Paketen. \\
\textbf{Nachteile:} Keine formale Klassenvalidierung; fehleranfällig bei großen Projekten.

\subsubsection{S4 -- Formales Klassen-System}

S4 ist ein formales OOP-System mit expliziter Klassendefinition, Slot-Validierung und Mehrfachvererbung. Es wird vor allem in Bioinformatik-Paketen (Bioconductor) eingesetzt.

\textbf{Schlüsselunterschiede zu S3:}
\begin{itemize}
  \item \textbf{Formale Deklaration} via \texttt{setClass} -- Slots (Felder) und ihre Typen sind explizit definiert
  \item \textbf{Slot-Zugriff} via \texttt{@} (nicht \texttt{\$})
  \item \textbf{Validierung} via \texttt{validity}-Argument möglich
  \item \textbf{Mehrfachvererbung} via \texttt{contains}
  \item \textbf{Multiple Dispatch}: \texttt{setMethod} kann auf der Kombination mehrerer Argument-Typen dispatchen
\end{itemize}

\textbf{Vor- und Nachteile:} Formal, sicher und gut dokumentierbar, aber verbos und deutlich komplexer als S3.

\subsubsection{R5 / Reference Classes -- Mutable OOP}

Reference Classes (auch R5) bringen \textbf{echte Referenzsemantik} nach R -- ähnlich wie Klassen in Python oder Java. Objekte sind mutable: Methoden können Felder in-place ändern (kein Copy-on-Modify).

\textbf{Vor- und Nachteile:} Referenzsemantik kann in manchen Situationen (z.\,B.\ Zustandsautomaten, Caches) eleganter sein. Allerdings ungewohnt für R-Programmierer; Debugging schwieriger; kaum in Standard-Paketen verwendet.

\subsubsection{R6 -- Modernes, schlankes Referenz-System}

Das Paket \texttt{R6} bietet eine moderne Alternative zu R5 mit saubererer Syntax, echter privater/öffentlicher Felddefinition und besserer Performance.

\subsubsection{Vergleichstabelle der OOP-Systeme}

  \centering

    \textbf{Merkmal}    & \textbf{S3} & \textbf{S4} & \textbf{R5}   & \textbf{R6} \\
    \midrule
    Formale Deklaration & --          & \checkmark  & \checkmark    & \checkmark  \\
    Referenzsemantik    & --          & --          & \checkmark    & \checkmark  \\

  \item \textbf{S3} für einfache Pakete und schnelle Prototypen -- die Default-Wahl in R
  \item \textbf{S4} wenn formale Typsicherheit und Multiple Dispatch benötigt werden (z.\,B.\ Bioconductor)
  \item \textbf{R6} wenn Zustandsverwaltung mit echter Kapselung gewünscht ist -- am nächsten an Python/Java-OOP
  \item \textbf{R5} heute weitgehend durch R6 ersetzt

\subsection{Tidyverse -- Philosophie \& Funktionsweise}

\subsubsection{Was ist das Tidyverse?}

Das Tidyverse ist ein \textbf{kohärentes Ökosystem von R-Paketen}, das von Hadley Wickham und dem RStudio (heute Posit) Team entwickelt wurde. Es teilt eine gemeinsame Design-Philosophie, konsistente API und Datenstruktur. Kernpakete sind: \texttt{ggplot2}, \texttt{dplyr}, \texttt{tidyr}, \texttt{readr}, \texttt{purrr}, \texttt{tibble}, \texttt{stringr}, \texttt{forcats}.

\subsubsection{Die Kernphilosophie: Tidy Data}

Das Tidyverse basiert auf dem Konzept \textbf{Tidy Data} (Hadley Wickham, 2014):
\begin{enumerate}
  \item Jede \textbf{Variable} bildet eine \textbf{Spalte}
  \item Jede \textbf{Beobachtung} bildet eine \textbf{Zeile}
  \item Jeder \textbf{Wert} steht in genau \textbf{einer Zelle}
\end{enumerate}

Tidy Data ist das standardisierte Eingabeformat für alle Tidyverse-Funktionen und eliminiert das häufige Reshaping, das in Base-R notwendig wäre.

\subsubsection{Das Tibble -- moderner Data Frame}

\texttt{tibble} ist eine überarbeitete Version des Data Frames mit besserem Druck-Verhalten, strikterer Subsetting-Semantik (kein automatisches Type-Dropping) und schnellerer Erstellung.

\subsubsection{dplyr -- Data Manipulation}

\texttt{dplyr} stellt fünf \textbf{Kern-Verben} bereit, die die häufigsten Datentransformationen abdecken:
\begin{itemize}
  \item \textbf{filter():} Zeilen filtern
  \item \textbf{select():} Spalten auswählen
  \item \textbf{mutate():} Neue Spalte berechnen
  \item \textbf{arrange():} Sortieren
  \item \textbf{summarise():} Aggregieren
\end{itemize}

\textbf{Der Pipe-Operator:} Zentrales Stilelement ist der Pipe-Operator \texttt{|>} (seit R 4.1) oder \texttt{\%>\%} (aus \texttt{magrittr}). Der Pipe übergibt das Ergebnis der linken Seite als erstes Argument der rechten Seite -- eine links-nach-rechts-lesbare Kette von Transformationen.

\textbf{Gruppierung und Aggregation:} \texttt{group\_by()} + \texttt{summarise()} ermöglichen komplexe Aggregationen pro Gruppe.

\subsubsection{tidyr -- Daten in Tidy Format}

\texttt{tidyr} bietet Funktionen zum Reshaping:
\begin{itemize}
  \item \texttt{pivot\_longer():} Wide $\to$ Long Format (häufig nötig für ggplot2)
  \item \texttt{pivot\_wider():} Long $\to$ Wide Format
  \item \texttt{unnest():} Verschachtelte Daten expandieren
\end{itemize}

\subsubsection{ggplot2 -- Grafiken nach dem Grammar of Graphics}

\texttt{ggplot2} implementiert die \textbf{Grammar of Graphics}: Ein Plot wird aus Schichten (Layers) aufgebaut, bestehend aus Daten (\texttt{aes}thetics) und geometrischen Objekten (\texttt{geom}s). Das ermöglicht eine deklarative, konsistente Beschreibung beliebig komplexer Grafiken.

In Base-R würde dieselbe Grafik \texttt{plot()}, \texttt{points()}, \texttt{lines()}, \texttt{legend()} etc.\ erfordern -- jedes Mal mit manueller Koordination.

\subsubsection{purrr -- Funktionale Programmierung}

\texttt{purrr} bietet eine konsistente Familie von \texttt{map\_*}-Funktionen als typsichere Alternative zu \texttt{lapply}/\texttt{sapply}:
\begin{itemize}
  \item \texttt{map()} gibt immer eine Liste zur\u00fcck
  \item \texttt{map\_dbl():} Ergebnis ist garantiert ein double-Vektor
  \item \texttt{map2():} Zwei Listen parallel verarbeiten
\end{itemize}

Das \texttt{~}-Syntax erzeugt eine anonyme Funktion (\texttt{.x} referenziert das aktuelle Element).

\subsubsection{Vorteile gegenüber plain R}

  \centering
  \begin{tabularx}{\linewidth}{L{3.5cm} L{5.2cm} L{5.2cm}}
    \textbf{Aspekt} & \textbf{Base R}                             & \textbf{Tidyverse}                 \\
    \midrule
    Lesbarkeit      & Verschachtelter Code                        & Lineare Pipe-Kette                 \\

\subsubsection{Nachteile und Kritik}

\begin{itemize}
  \item \textbf{Abhängigkeiten:} Das Tidyverse bringt viele Pakete mit -- Dependency-Management kann aufwändig sein
  \item \textbf{Performance:} \texttt{dplyr} kann bei sehr großen Datensätzen langsamer sein als spezialisierte Pakete wie \texttt{data.table}
  \item \textbf{Non-standard Evaluation (NSE):} \texttt{dplyr} nutzt NSE -- elegant, aber erschwert programmatische Nutzung in Funktionen
  \item \textbf{Versionsstabilität:} Das Tidyverse entwickelt sich schnell; Breaking Changes erfordern Code-Aktualisierung
\end{itemize}

\subsection{Wichtige Dateiformate}

Dateiformate spielen eine zentrale Rolle bei Datenspeicherung, -austausch und -verarbeitung. Sie lassen sich nach mehreren Dimensionen klassifizieren: \textbf{Text vs. Binär} -- Textformate (CSV, JSON, YAML, XML) sind menschenlesbar und mit Standard-Editoren bearbeitbar; Binärformate (HDF5, Parquet, Pickle) sind kompakt und schneller zu verarbeiten. \textbf{Hierarchisch vs. tabellarisch} -- XML, JSON, YAML können beliebig tiefe Strukturen darstellen; CSV und Parquet sind auf flache Tabellen optimiert. \textbf{Schema vs. schemalos} -- XML unterstützt formale Schemata (XSD); JSON Schema ist optional; CSV und YAML sind vollständig schemalos.

\textbf{CSV (Comma-Separated Values)} ist das universellste Format für tabellarische Daten. Jede Zeile repräsentiert einen Datensatz; Felder werden durch ein Trennzeichen (meist Komma, in deutschsprachigen Ländern oft Semikolon) getrennt. Der Vorteil liegt in universeller Kompatibilität, Lesbarkeit und praktisch null Parsing-Overhead. Nachteile: Kein Typ-System, keine Unterstützung für Hierarchien, Encoding-Probleme (UTF-8 vs. Latin-1), und große CSV-Dateien sind langsam zu lesen, weil der gesamte Inhalt als Text vorliegt.

\textbf{XML (eXtensible Markup Language)} ist hierarchisch und textbasiert. Daten werden in verschachtelten Tags eingeschlossen. XML ist sehr ausdrucksstark und unterstützt formale Validierung via XSD-Schemata, was es im Unternehmensumfeld verbreitet macht. Nachteil: Sehr verbose (viel Overhead durch Tags), schwer zu lesen, teuer zu parsen im Vergleich zu modernen Alternativen.

\textbf{JSON (JavaScript Object Notation)} hat XML als Web-Standard weitgehend verdrängt. JSON ist kompakt, direkt auf Programmiersprachenstrukturen (Dicts, Arrays, Primitives) abbildbar und leichter zu parsen. REST-APIs verwenden fast ausschließlich JSON. Das Konzept ist einfach: ein Objekt ist eine Key-Value-Sammlung (\texttt{\{...\}}), ein Array ist eine Sequenz (\texttt{[...]}), und atomic Typen sind String, Zahl, Boolean, Null. Einschränkungen: Keine Kommentare, keine nativen Datumstypen, keine Unterscheidung zwischen Integer und Float auf Protokoll-Ebene.

\textbf{YAML (YAML Ain't Markup Language)} ist eine Obermenge von JSON und wurde für maximale menschliche Lesbarkeit optimiert. Einrückung definiert die Hierarchie; Anführungszeichen sind optional; Listen und Dicts sind intuitiv. Typische Einsätze sind Konfigurationsdateien (Docker Compose, Kubernetes, GitHub Actions, Ansible, CI/CD). Ein großes Problem ist, dass YAML-Parsing komplex und fehleranfällig ist. Kritisch für Sicherheit: \textbf{Immer \texttt{yaml.safe\_load()} verwenden, nie \texttt{yaml.load()}} aus unbekannten Quellen! Der ursprüngliche \texttt{yaml.load()} kann beliebigen Code ausführen (Pickle-Problem).

\textbf{HDF5 (Hierarchical Data Format)} ist ein binäres, hierarchisches Format. Eine HDF5-Datei ist wie ein Dateisystem: es gibt \textbf{Groups} (Verzeichnisse) und \textbf{Datasets} (n-dimensionale Arrays). Eigenschaften (Metadaten) können an beide angehängt werden. Warum HDF5 für ML? \textbf{Lazy Loading} -- nur angeforderte Daten werden vom Disk geladen. Keras speichert Modellgewichte in HDF5. NumPy-Arrays werden direkt gespeichert mit vollständiger Typ-Information. Kompression ist integriert. Nachteile: Nicht human-readable, Parallelschreiben eingeschränkt, weniger flexibel als Parquet.

\textbf{Apache Parquet} ist spaltenorientiert und aus dem Hadoop-Ökosystem. Der zentrale Vorteil: Alle Werte einer Spalte werden zusammen gespeichert. Das macht es extrem effizient bei Lesezugriffen auf wenige Spalten (typisch OLAP-Workload) -- um auf 5 von 100 Spalten zuzugreifen, liest man nur diese 5, nicht den ganzen Datensatz. Integrierte Kompression und vollständiges Typ-System. Standard in Apache Spark, AWS Athena, Google BigQuery, DuckDB. Im Gegensatz zu HDF5 ist Parquet spezialisiert auf Tabellendaten.

Weitere Formate: \textbf{Pickle} ist Pythons natives Serialisierungsformat, praktisch aber \textbf{sicherheitskritisch} -- nie aus unbekannten Quellen laden! \textbf{NetCDF} ist der Standard in Klimawissenschaft und Meteorologie für multidimensionale Array-Daten.

\begin{table}[h!]
  \centering
  \begin{tabular}{p{1.8cm} p{1.3cm} p{4.3cm} p{5.3cm}}
    \textbf{Format} & \textbf{Typ} & \textbf{Stärken}             & \textbf{Schwächen}                 \\
    \midrule
    CSV             & Text         & Universell, einfach          & Kein Typ-System, langsam bei groß  \\
    JSON            & Text         & Kompakt, Standard für APIs   & Keine Kommentare, kein Datumstyp   \\
    XML             & Text         & Hierarchie, validierbar      & Verbose, Parsing komplex           \\
    YAML            & Text         & Human-lesbar, Configs        & Parsing fehleranfällig             \\
    HDF5            & Binär        & Hierarchie, Lazy Loading     & Nicht human-readable, Speicher     \\
    Parquet         & Binär        & Spaltenorientiert, effizient & Nur Tabellen, Big-Data Tools nötig \\
  \end{tabular}
\end{table}

\subsection{git}

\subsubsection{Was ist Git?}

Git ist ein \textbf{verteiltes Versionskontrollsystem} (DVCS), ursprünglich 2005 von Linus Torvalds geschrieben. Im Gegensatz zu zentralisierten Systemen (SVN, CVS) hat jeder Entwickler eine \textbf{vollständige Kopie} des Repositories -- inkl. kompletter Historie -- auf seinem Rechner.

\subsubsection{Kernkonzepte}

\textbf{Das Git-Objektmodell:} Git speichert \textbf{Snapshots}, nicht Deltas. Vier Objekttypen im \texttt{.git/objects/}:
\begin{itemize}
  \item \textbf{Blob:} Dateiinhalt (beliebige Binärdaten)
  \item \textbf{Tree:} Verzeichnisstruktur (Liste von Blobs und Sub-Trees)
  \item \textbf{Commit:} Snapshot eines Projektzustands mit Author, Zeitstempel, Parent-Commit
  \item \textbf{Tag:} Benannte Referenz auf einen Commit (z.B. \texttt{v1.0.0})
\end{itemize}

Alle Objekte werden durch SHA-1-Hash (40-stellige Hex-Zeichenkette) identifiziert. Jede Änderung ergibt einen neuen Hash -- Historia ist kryptographisch manipulationssicher.

\textbf{Die drei Bereiche:}
\begin{itemize}
  \item \textbf{Working Directory:} Deine Dateien auf der Festplatte
  \item \textbf{Staging Area:} Zwischenspeicher für \texttt{git add} -- man wählt aus, was in den nächsten Commit geht
  \item \textbf{Repository (.git/):} Die lokale Datenbank mit aller Historie
\end{itemize}

\subsubsection{Branches und Merging}

Ein \textbf{Branch} ist nur ein Zeiger auf einen Commit. Erstellen ist eine $\mathcal{O}(1)$-Operation -- kein Kopieren von Dateien.

\textbf{Merge:} Zwei Commit-Linien zusammenführen. Zwei Typen:
\begin{itemize}
  \item \textbf{Fast-Forward:} Wenn eine Branch einfach weiter vorne ist, wird der Zeiger verschoben
  \item \textbf{Rebase:} Alternative -- schreibt Commits so um, als wären sie auf aktuellem Stand entstanden. Erzeugt lineare Geschichte, verändert aber SHA-1-Hashes (daher nicht auf shared Branches!)
\end{itemize}

\subsubsection{Basisbefehle}

\textbf{Repository einrichten:}
\begin{itemize}
  \item \texttt{git init} -- Neues lokales Repo erstellen
  \item \texttt{git clone <url>} -- Bestehendes Repo klonen
\end{itemize}

\textbf{Status und Unterschiede:}
\begin{itemize}
  \item \texttt{git status} -- Zustand anzeigen
  \item \texttt{git diff} -- Änderungen im Working Dir
  \item \texttt{git log --oneline --graph} -- Geschichte mit Branch-Grafik
\end{itemize}

\textbf{Änderungen erfassen:}
\begin{itemize}
  \item \texttt{git add <datei>} -- Datei stagen
  \item \texttt{git add -p} -- Interaktiv: nur bestimmte Hunks
  \item \texttt{git commit -m Nachricht} -- Commit mit Message
  \item \texttt{git commit --amend} -- Letzten Commit korrigieren
\end{itemize}

\textbf{Branches:}
\begin{itemize}
  \item \texttt{git branch} -- Branches auflisten
  \item \texttt{git switch -c <branch>} -- Branch erstellen und wechseln
  \item \texttt{git merge <branch>} -- Mergen
  \item \texttt{git rebase main} -- Rebasing
\end{itemize}

\textbf{Remote-Operationen:}
\begin{itemize}
  \item \texttt{git fetch origin} -- Änderungen vom Remote holen (OHNE merge)
  \item \texttt{git pull origin main} -- fetch + merge
  \item \texttt{git push origin main} -- Commits zum Remote senden
\end{itemize}

\textbf{Rückgängig machen:}
\begin{itemize}
  \item \texttt{git restore <datei>} -- Working-Dir-Änderung verwerfen
  \item \texttt{git revert <hash>} -- Neuen Commit erstellen, der Commit rückgängig macht
  \item \texttt{git reset --hard HEAD\textasciitilde 1} -- Letzten Commit rückgängig (DATEN VERLOREN!)
  \item \texttt{git reflog} -- Rettungsanker nach \texttt{reset --hard}
\end{itemize}

\subsubsection{Workflow und Best Practices}

\textbf{Typischer Feature Branch Workflow:}
\begin{enumerate}
  \item \texttt{git switch main \&\& git pull origin main}
  \item \texttt{git switch -c feature/my-feature}
  \item Entwickeln und committen
  \item \texttt{git push -u origin feature/my-feature}
  \item Pull Request erstellen für Code Review
  \item Nach Merge: \texttt{git branch -d feature/my-feature}
\end{enumerate}

\textbf{.gitignore:} Definiert, welche Dateien Git ignorieren soll. Typische Einträge:
\begin{itemize}
  \item \texttt{\_\_pycache\_\_/}, \texttt{*.pyc}, \texttt{.venv/} (Python)
  \item \texttt{data/raw/}, \texttt{*.csv}, \texttt{*.h5}, \texttt{*.pkl} (Daten -- nutze Git LFS oder DVC!)
  \item \texttt{.vscode/}, \texttt{.idea/} (IDE)
\end{itemize}
